this was the original complaint:

1. Envelope encryption / per-tenant data keys

Present, and it is the most developed of the five. It is derivation-based rather than
stored-wrapped-DEK.

- backend/custody/wrapping.py, inner layer. app_secret() (:65) pulls the seed from the dstack
KMS over the guest-agent socket (get_key(APP_KEY_PATH, purpose="seal")), cached per process.
derive() (:98) is the only HKDF. inner_key() (:109) salts with f"{uid}|{key_version}", so
the per-tenant key is derived, never stored. seal_inner/open_inner are AES-GCM with uid as
AAD.
- cosigner/keys.py, outer layer, different box, different operator. master_key() (:109) comes
from systemd LoadCredentialEncrypted= (TPM-sealed, deploy/hetzner/cosigner.service:29-30).
outer_key() (:127) is HKDF(master, salt=uid, info="outer"). wrap/unwrap (:135, :147), uid as
AAD, so an outer cannot be replayed under another tenant's id.
- Layer order (ours inside, theirs outside) is the property; asserted in prose in
cosigner/__init__.py and backend/custody/tokens.py:165 take_custody.
- Record format: backend/custody/tokens.py:109 encode_record, LLTK | record_version | 
key_version | outer.

There is no per-tenant DEK for anything other than the Gmail refresh token. Voice profiles,
personal context, database/accounts.json, state/, drafts and the audit DB are plaintext on
disk, protected only by 0700/0600 and the letterlock uid (account.py:130 secure_dir, :139 
_write_manifest, tokens.py:138 store_record). PII lives in those files; the envelope scheme
does not cover them.

2. Authorization enforcement

No RLS, no OPA/Cedar/OpenFGA. There is no database engine, the store is
database/accounts.json plus per-account directories (backend/accounts/account.py:55-56). The
only SQLite in the tree is the co-signer's audit log.

What exists, in two disjoint places:

whatchamacallit, repeated ~25 times as acct = self._require_auth(), rather than per-route
ownership predicates. Authorization is binary, signed in or not. No roles; the only owner
special case is owner_account() (account.py:149), used solely by the seed and the test
harness.
- Custody-side, honet-schmonest policy engine: cosigner/policy.py:172 authorize() is the
closest thing to a policy decision point in the codebase. Every co-signer request goes
through it, ordered kill switch → attestation verdict → request shape → wrap-once → rate
limit, and the same call under the same lock writes the audit row. cosigner/attest.py:157 
verify_client and backend/tee/quote_policy.py are the attestation half, with allowlists as
data files (cosigner/allowlist.json, backend/integrations/inference_allowlist.json).

4. Audit log schema and retention

One log, custody only.

- Schema at cosigner/audit.py:31: requests(id, ts, uid, action, decision, reason,
fingerprint, measurement, attested), indexed on (uid, action, ts) and ts. Written only by
record() (:93), which takes no parameter that could carry key or ciphertext material;
tests/test_cosigner.py:289 asserts the column set.
- Append-only by convention only, the docstring says so (:9-14); no triggers, no
separate-rights connection.
- The table doubles as rate-limiter state (granted_since, :110; ever_granted, :126). That is
a deliberate single source of truth, but it means retention and the limiter are coupled: any
pruning of rows older than an hour is safe, anything else changes enforcement, and truncation
resets the wrap-once check at policy.py:129.
- No retention exists. No pruning, no VACUUM, no logrotate, no off-box copy in any unit or
timer (deploy/hetzner/ has no audit timer). audit.py:12 explicitly defers the copy-off-box to
the operator. audit.db is 0600 in StateDirectory=cosigner (0700).

provider switches, Telegram linking, voice/personal-context edits, account deletion, or
drafts sent. Those paths only write to stderr via log() into the journal, which is
unstructured and rotates on the host's default.

Three distinct channels, each with one reader.

the provisioned-ness definition shared by tee_boot.run_gate() and deploy/preflight.py.

  3. Key rotation and lifecycle

  Anticipated in the schema, not implemented anywhere.

  - wrapping.KEY_VERSION = 1 (:36) and keys.KEY_VERSION = 1 (:56). Version travels with the
  record, so old records stay identifiable.
  - Asymmetry: the inner layer can decrypt at an old version, open_inner(uid, inner, 
  key_version) takes the version from the record (tokens.py:290, :293). The outer layer cannot:
  keys.outer_key (:129) and keys.unwrap (:157) both assert version == KEY_VERSION. So bumping
  the co-signer's version makes every existing record unopenable, which contradicts the comment
  at keys.py:54 claiming the prefix exists so the master key can be rotated.
  - There is no re-wrap or re-seal routine anywhere. grep -rn "rotat" finds only comments.
  cosigner.service:13-15 states the consequence plainly: rotating either key means
  re-onboarding every user.

  right guard but is dev-only.
  - Session secret has no key id in the cookie (session.py:64 _signed), so rotating
  SESSION_SECRET logs everyone out; no overlapping-key window.

  nonces, and attestation verdict caches keyed on measurement identity

  4. Audit log schema and retention

  One log, custody only.

  - Schema at cosigner/audit.py:31: requests(id, ts, uid, action, decision, reason,
  fingerprint, measurement, attested), indexed on (uid, action, ts) and ts. Written only by

  tests/test_cosigner.py:289 asserts the column set.

  separate-rights connection.
  - The table doubles as rate-limiter state (granted_since, :110; ever_granted, :126). That is
  a deliberate single source of truth, but it means retention and the limiter are coupled: any
  pruning of rows older than an hour is safe, anything else changes enforcement, and truncation

  - No retention exists. No pruning, no VACUUM, no logrotate, no off-box copy in any unit or

"""PII pseudonymization for content sent to the external LLM.

Single source of truth for masking PII before it leaves the server and
restoring it afterwards. Entities are replaced with numbered tags
([PERSON1], [EMAIL1], ...) via a Presidio custom operator. One shared
state dict per draft keeps the same real value mapped to the same tag
across the input email and every tool result in that draft.

The mapping is the sensitive artifact: it lives in memory for the
duration of a single draft() call and is discarded after restore. It is
never persisted and never sent to the model.

Flip PSEUDONYMIZE_ENABLED to turn the whole layer on. When off, every
function here is a passthrough and Presidio is never imported.
"""

import re
import sys

USER_FIRST = "Morgan"
USER_LAST = "Rivers"
USER_FIRST_ALIASES = ["Daniel"]
USER_EMAILS = ["danielmorganrivers@gmail.com"]

# profile + address book. Empty in single-tenant so DEFAULT_IDENTITY is unchanged.

USER_CONTACTS = []

USER_LAST_TAG = "[USER_LAST]"

# A phone-like run: a digit, then 5+ of digit/space/()-.+, then a digit, not
# glued to word characters. Candidates are digit-normalized before comparison so
# spacing, dashes, dots, parens, and +country-code all match one configured number.
_PHONE_RUN = re.compile(r"(?<!\w)\+?\d[\d\s().\-]{5,}\d(?!\w)")
_MIN_PHONE_DIGITS = 7


def _digits(s):
    return re.sub(r"\D", "", s)

class UserIdentity:
    """Per-user masking identity: the account owner's own name/email, which
    are deterministically tagged before Presidio so the owner never varies by
    person-numbering. Compiled once per identity; passed into new_state so a
    shared process can hold one identity per user without global coupling."""

    def __init__(self, first, last, first_aliases=(), emails=(), phones=(), contacts=(), account_id="default",
                 analyzer=True):
        assert first and last, "identity requires first and last name"
        assert account_id, "identity requires an account_id"
        self.account_id = account_id
        self.analyzer = bool(analyzer)
        self.first = first
        self.last = last
        self.first_aliases = list(first_aliases)
        self.emails = list(emails)
        self.contacts = [" ".join(c.split()) for c in contacts if c.strip()]
        # Kept so an identity can be copied faithfully. Masking uses the digit
        # runs below; without the originals a copy silently loses every phone,
        # which is a masking gap rather than a cosmetic one.
        self.phones = list(phones)
        self._phone_digits = []
        for p in phones:
            d = _digits(p)
            assert len(d) >= _MIN_PHONE_DIGITS, f"phone {p!r} has too few digits to mask safely"
            self._phone_digits.append(d)
        self._rules = self._build_rules()

    def _build_rules(self):
        firsts = [self.first] + self.first_aliases
        rules = []
        for f in firsts:
            rules.append((
                re.compile(rf"\b{re.escape(f)}\s+{re.escape(self.last)}\b", re.IGNORECASE),
                f"{USER_FIRST_TAG} {USER_LAST_TAG}",
            ))
        for e in self.emails:
            rules.append((re.compile(re.escape(e), re.IGNORECASE), USER_EMAIL_TAG))
        rules.append((re.compile(rf"\b{re.escape(self.last)}\b"), USER_LAST_TAG))
        for f in firsts:
            rules.append((re.compile(rf"\b{re.escape(f)}\b"), USER_FIRST_TAG))
        return rules

    def mask_user(self, text):
        for rx, repl in self._rules:
            text = rx.sub(repl, text)
        return self._mask_phones(text)

    def _mask_phones(self, text):
        if not self._phone_digits:
            return text

        def repl(m):
            cand = _digits(m.group(0))
            if len(cand) < _MIN_PHONE_DIGITS:
                return m.group(0)
            for pd in self._phone_digits:
                if cand == pd or cand.endswith(pd) or pd.endswith(cand):
                    return USER_PHONE_TAG
            return m.group(0)

        return _PHONE_RUN.sub(repl, text)

    def seed_mapping(self):
        mapping = {USER_FIRST_TAG: self.first, USER_LAST_TAG: self.last}
        if self.emails:
            mapping[USER_EMAIL_TAG] = self.emails[0]
        if self._phone_digits:
            mapping[USER_PHONE_TAG] = self._phone_digits[0]
        return mapping

def analyzer_available():
    """Whether this box can run the Presidio + spaCy analyzer at all.

    Checked by module presence, never by importing: `import presidio_analyzer`
    pulls spaCy in behind it and costs ~470 MB before a model is even loaded,
    which is the whole reason a small box turns this off. The web UI uses this
    to decide whether the setting is selectable or shown locked."""
    if not PSEUDONYMIZE_ENABLED:
        return False
    for module in ("presidio_analyzer", "presidio_anonymizer", SPACY_MODEL):
        try:
            if importlib.util.find_spec(module) is None:
                return False
        except (ImportError, ValueError):
            return False
    return True


def _build_engines():
    from presidio_analyzer import AnalyzerEngine, Pattern, PatternRecognizer
    from presidio_analyzer.nlp_engine import NlpEngineProvider
    from presidio_anonymizer import AnonymizerEngine
    from presidio_anonymizer.operators import Operator, OperatorType

    class Pseudonymize(Operator):
        def operate(self, text, params):
            etype = params["entity_type"]
            if etype == "PERSON":
                return params["pindex"].get(text.lower().strip(), text)
            return _tag_value(params, etype, text)

        def validate(self, params):
            pass

        def operator_name(self):
            return "pseudonymize"

        def operator_type(self):
            return OperatorType.Anonymize

    nlp_config = {
        "nlp_engine_name": "spacy",
        "models": [{"lang_code": "en", "model_name": SPACY_MODEL}],
    }
    nlp_engine = NlpEngineProvider(nlp_configuration=nlp_config).create_engine()
    analyzer = AnalyzerEngine(nlp_engine=nlp_engine, supported_languages=["en"])

    grouped = defaultdict(list)
    for entity, name, regex, score in SECRET_PATTERNS:
        grouped[entity].append(Pattern(name=name, regex=regex, score=score))
    for entity, patterns in grouped.items():
        analyzer.registry.add_recognizer(
            PatternRecognizer(supported_entity=entity, patterns=patterns)
        )

    anonymizer = AnonymizerEngine()
    anonymizer.operators_factory.add_anonymize_operator(Pseudonymize)
    return analyzer, anonymizer


def _engines():
    global _ANALYZER, _ANONYMIZER
    if _ANALYZER is None:
        _ANALYZER, _ANONYMIZER = _build_engines()
    return _ANALYZER, _ANONYMIZER


def _tag_value(state, etype, surface):
    """Assign, or reuse, the numbered tag standing in for one non-person value.

    Sole allocator of those tags: the Presidio operator and the regex-only path
    both come through here, so a value carries the same tag whichever path
    found it and the mapping restore() reads is written in one place."""
    assert etype, "tagging needs an entity type"
    key = (etype, surface.lower().strip())
    seen = state["seen"]
    if key not in seen:
        state["counters"][etype] += 1
        tag = f"[{etype}{state['counters'][etype]}]"
        seen[key] = tag
        state["mapping"][tag] = surface
    return seen[key]


def _pseudonymize_patterns(text, state):
    """Mask what regexes alone can find, for accounts running without the
    analyzer. Secrets first, so a key embedded in an address-shaped string is
    tagged as a key rather than half-eaten by the email rule."""
    assert state is not None, "pattern masking needs a state"
    for entity, rx in _SECRET_RULES:
        text = rx.sub(lambda m, e=entity: _tag_value(state, e, m.group(0)), text)
    text = _EMAIL_RUN.sub(lambda m: _tag_value(state, "EMAIL_ADDRESS", m.group(0)), text)

    def phone(m):
        if len(_digits(m.group(0))) < _MIN_PHONE_DIGITS:
            return m.group(0)
        return _tag_value(state, "PHONE_NUMBER", m.group(0))

    return _PHONE_RUN.sub(phone, text)


def new_state(identity=None):
    """Fresh shared mapping for one draft, or None when disabled.

    identity is the account owner whose own name/email get fixed tags; defaults
    to DEFAULT_IDENTITY so single-tenant callers need pass nothing. It also
    carries whether this account runs the analyzer; an account that asked for it
    on a box without it installed gets the regex-only path rather than a crash,
    which is why the flag is resolved here and not at the call site."""
    if not PSEUDONYMIZE_ENABLED:
        return None
    identity = identity or DEFAULT_IDENTITY
    return {
        "account_id": identity.account_id,
        "identity": identity,
        "analyzer": bool(identity.analyzer and analyzer_available()),
        "counters": defaultdict(int),
        "seen": {},
        "mapping": identity.seed_mapping(),
        "names": {},
        "pindex": {},
        "persons": {},
        "token_index": {},
    }


def _person_tag(state, pid, surface, preferred_role):
    p = state["persons"][pid]
    key = surface.lower()
    if key in p["surftag"]:
        return p["surftag"][key]
    role = preferred_role
    if role in p["roles"]:
        n = 1
        while f"X{n}" in p["roles"]:
            n += 1
        role = f"X{n}"
    p["roles"][role] = surface
    tag = f"[PERSON{pid}_{role}]"
    p["surftag"][key] = tag
    state["mapping"].setdefault(tag, surface)
    state["names"].setdefault(surface, tag)
    state["pindex"].setdefault(key, tag)
    state["token_index"][key] = pid
    return tag


def _new_person(state):
    state["counters"]["PERSON"] += 1
    pid = state["counters"]["PERSON"]
    state["persons"][pid] = {"roles": {}, "surftag": {}}
    return pid


def _resolve_full(state, surface):
    tokens = [t for t in surface.split() if t]
    pid = None
    for t in tokens:
        pid = state["token_index"].get(t.lower())
        if pid:
            break
    if pid is None:
        pid = _new_person(state)
    n = len(tokens)
    parts = []
    for i, t in enumerate(tokens):
        if _stop(t):
            parts.append(t)
            continue
        role = "FIRST" if i == 0 else ("LAST" if i == n - 1 else f"MID{i}")
        parts.append(_person_tag(state, pid, t, role))
    comp = " ".join(parts)
    state["names"].setdefault(surface, comp)
    state["pindex"].setdefault(surface.lower(), comp)
    return comp


def _resolve_single(state, surface):
    if _stop(surface):
        return surface
    pid = state["token_index"].get(surface.lower())
    if pid is None:
        pid = _new_person(state)
    return _person_tag(state, pid, surface, "FIRST")


def _resolve_persons(state, results, text):
    surfaces = []
    for r in results:
        if r.entity_type == "PERSON":
            s = text[r.start:r.end].strip()
            if s:
                surfaces.append(s)
    surfaces.sort(key=lambda s: len(s.split()), reverse=True)
    for s in surfaces:
        if s.lower() in state["pindex"]:
            continue
        if len(s.split()) >= 2:
            _resolve_full(state, s)
        else:
            _resolve_single(state, s)


def _scrub_contacts(text, state):
    """Deterministically tag known contact names before Presidio, so the
    finite set of the owner's contacts is masked even when NER misses them.

    Formatting-variant tolerant (case + internal whitespace). Each contact is
    routed through the same person machinery as NER-detected names, so a contact
    and its later NER mentions collapse to one person id. Single-token contacts
    that collide with a stopword are left alone to avoid nuking common words."""
    for surface in state["identity"].contacts:
        tokens = surface.split()
        if not tokens:
            continue
        pat = re.compile(r"\b" + r"\s+".join(re.escape(t) for t in tokens) + r"\b", re.IGNORECASE)
        if not pat.search(text):
            continue
        if surface.lower() not in state["pindex"]:
            if len(tokens) >= 2:
                _resolve_full(state, surface)
            elif not _stop(surface):
                _resolve_single(state, surface)
        comp = state["pindex"].get(surface.lower())
        if comp:
            text = pat.sub(comp, text)
    return text


def _mask_names(text, state):
    names = state["names"]
    for surface in sorted(names, key=len, reverse=True):
        text = re.sub(rf"\b{re.escape(surface)}\b", names[surface], text)
    return text


def pseudonymize(text, state):
    """Replace PII in text with numbered tags, growing the shared state.

    The owner's own name/email/phone and known contact names are scrubbed
    deterministically before Presidio (literal match, formatting-variant
    tolerant), so the finite highest-stakes set is masked regardless of what NER
    catches. Names seen earlier in the draft are re-masked so a name cannot drift
    to a new tag. Presidio then
    detects any new PII; _resolve_persons groups co-referent name fragments
    under one person id and decomposes each into first/last role tags, so the
    model sees [PERSON1_FIRST] / [PERSON1_LAST] as the same identity.

    With the analyzer off, the deterministic layers above still run and the
    secret, email and phone regexes replace it, so the owner's own identifiers,
    known contacts, and anything key-shaped are still masked. What is lost is
    detection of people, places and organisations this account has never
    corresponded with before.

    Passthrough when disabled or when text is empty.
    """
    if state is None or not text:
        return text

    text = state["identity"].mask_user(text)
    text = _scrub_contacts(text, state)
    text = _mask_names(text, state)
    if not state["analyzer"]:
        return _pseudonymize_patterns(text, state)

    from presidio_anonymizer.entities import OperatorConfig

    analyzer, anonymizer = _engines()
    results = analyzer.analyze(text=text, language="en", entities=ENTITIES)
    if results:
        _resolve_persons(state, results, text)
        text = anonymizer.anonymize(
            text=text,
            analyzer_results=results,
            operators={"DEFAULT": OperatorConfig("pseudonymize", state)},

    return text


def restore(text, state):
    """Replace tags with their original values, longest-tag-first.

    Longest-first prevents [PERSON1] from clobbering [PERSON11].
    Passthrough when disabled or when text is empty.
    """
    if state is None or not text:
        return text
    mapping = state["mapping"]
    for tag in sorted(mapping, key=len, reverse=True):
        text = text.replace(tag, mapping[tag])
    return text

❯ without looking at the repo: what are the main ways security failues happen, and how does one prioritize and triage security issues in general, and for this kind of app in particular       

● How security failures actually happen

  Most incidents come from a small number of classes, roughly in order of how often they cause serious loss:

  Authorization, not authentication. Login usually works. What fails is the per object ownership check: an id arrives from the browser, the handler acts on it without asking whether the
  signed-in user owns it. This is the single most common cause of cross-tenant data loss in web apps.

  Credential handling. Long lived, broad scope, silently usable credentials that leak into logs, backups, error reports, subprocess environments, or a component that had no business holding
  them. Compounded by no rotation story, so a suspected leak has no cheap response.

  Trust boundary drawn in the wrong place. Not a bug in any one line. A component holds more privilege than its inputs justify, so it becomes a confused deputy: it faithfully executes what an
  untrusted party asked for, with authority that party lacks.

  Injection at a parser boundary. Any place where structured meaning is built by string concatenation: SQL, shell, HTML, search query languages, template engines, and now natural language
  prompts. The tell is that data and control share a channel with no escaping contract you can rely on.

  Multi-step flows. OAuth callbacks, checkout confirmation, account linking, password reset. Each step has to be bound to the session and to the previous step. Missing bindings give you
  replay, code substitution, and "link the attacker's object to my account" bugs. Races belong here too.

  Failing open. Exception handlers that swallow a verification error and continue. Fallbacks that substitute a less safe path when the safe one is unavailable. Positive verdicts cached on a
  key that is too coarse. This class is dangerous because the system looks healthy while enforcing nothing.

  Operational and supply chain. File modes, service accounts, exposed ports, stale hosts, dependencies pulled by tag, secrets in a unit file. Boring and constant.

  Deletion and retention. Data that survives account deletion, or lives in a place nobody enumerated. Rarely exploited, frequently a legal and reputational problem.

  How to prioritize in general

  Do not rank by CVSS or scanner counts. Rank by three questions asked in order.

  1. Who can trigger it. Anonymous internet, any registered user, a user who already has some relationship to the victim, or the operator. Each step down that list is roughly an order of
  magnitude less urgent.
  2. What it yields. Cross-tenant read or write, persistent credential, code execution, one user's own data, denial of service, information disclosure with no direct use.
  3. What must already be true. Preconditions that the attacker controls are not mitigations. Preconditions that require luck or insider access are.

  That gives a working order: pre-auth remote execution or cross-tenant access, then authenticated cross-tenant access, then persistent credential exposure, then privilege escalation inside a
  tenant, then self-inflicted or operator-only issues, then availability.

  Two modifiers worth applying on top:

  Detectability. A bug that leaves no trace is worse than an equally severe one that writes an audit row, because it changes what you can say after the fact and whether you can bound the
  damage.

  Fix durability. Prefer fixes that remove the class over fixes that patch a call site: a single chokepoint that all callers must pass through, a type that makes the unsafe state
  unrepresentable, or a test that fails in CI when the invariant breaks. A finding whose fix is "remember to check this in every new handler" has not really been fixed.

  Also useful: separate severity from confidence. A confirmed medium beats a speculative critical for scheduling purposes, and speculative findings should be verified before they consume
  anyone's time.

  For this class of app specifically

  A multi-tenant agent holding Gmail refresh tokens, driven by content strangers write, calling out to inference providers. The threat ranking is not the generic web one.

  1. Cross-account access. Highest, because the asset is other people's mailboxes. Every route and every account mutator must derive the account identity from the session, never from a path
  segment, form field, or webhook payload. The dangerous shape is any function that takes an account id as a parameter and is also reachable from a request. Related: background jobs that
  sweep all accounts and could deliver one account's result to another's Telegram target or draft.

  2. Refresh token custody. A Gmail refresh token is persistent, broad, silent, and survives your redeploys. It ranks above nearly every conventional web bug because compromise is unbounded
  in time and invisible to the victim. Things worth watching: any code path that materializes a plaintext refresh token into a long lived object, any log or exception that could carry one,
  and whether a compromise of a single component yields readable tokens. Split custody only pays off if the layer order holds and there is no bypass; a bypass added for availability reasons
  converts the whole design back into one box that can read everything.

  3. OAuth and linking flow integrity. State binding, PKCE, redirect allowlist, and the ownership test on anything the browser hands back: a checkout id, a link token, a chat id. The generic
  bug here is "user submits an identifier for an object they do not own, system links it to their account". It applies to billing, to Telegram linking, and to any future integration.

  4. Prompt injection and tool capability. Email bodies are attacker controlled by definition: anyone who knows the address gets to put text in front of your model. Assume the fence around
  untrusted content will eventually fail. So the question to prioritize is not "can the model be misled" but "what is the worst the available tools permit when it is". Rank findings by the
  capability they reach:

  - Ability to send mail to an attacker chosen recipient is the top one, because it is a direct exfiltration channel for everything the model can read.
  - Ability to search or read the rest of the mailbox and place that content anywhere an outsider can see it, including a reply on a thread the attacker started.
  - Ability to write to a shared or public calendar, or to any object outside a fixed, non addressable target.
  - Ability to spend money or trigger unbounded loops.

  Drafts only, fixed write targets, no attacker chosen recipients, and caps on field lengths are what make injection an annoyance rather than a breach. Treat any change that widens a tool's
  reach as a security change even when it looks like a feature.

  5. Data egress. Which third party sees plaintext mail, under what agreement, and whether that is what the user selected. Silent provider fallback is a security bug, not a resilience
  feature. Tracing, metrics, and error reporting are egress channels people forget. Masking failures are real but partial mitigations, so weight them below "sent to the wrong provider
  entirely".

  6. Verification that fails open. Attestation, signature checks, and policy decisions where the error path returns something other than refusal. Also caches keyed on a value that does not
  change when the verified thing changes, which turns one good verdict into a permanent pass for a pool of unverified peers.

  7. Web tier fundamentals. Session cookie signing and rotation, CSRF on state-changing routes, path traversal in static serving, and HTML injection wherever email content or user written
  documents get rendered back into a page. Ordinary severity, ordinary fixes.

  8. Deployment and process boundaries. File modes on token and database directories, which unix account each service runs as, secrets in journals, and whether a deploy can leave a stale file
  behind that still runs. Lower likelihood, but these are the findings that turn a medium into a critical by giving a foothold more reach than it should have.

  9. Retention and deletion. Whether deleting an account actually removes the derived paths, and whether logs that intentionally outlive an account carry more than they need to.

  Triage questions to ask of any finding here

  - Does it cross an account boundary?
  - Does it touch a refresh token, or the keys protecting one?
  - Is it reachable by someone who only knows a user's email address?
  - Is it reachable before sign in?
  - If the model is fully adversarial at this point, what does the surrounding code let it do?
  - Does the fix live at a chokepoint, or does it rely on future code remembering?

  Anything answering yes to the first four gets worked immediately. The last two decide whether the fix is finished.

● How security failures actually happen

  Most incidents come from a small number of classes, roughly in order of how often they cause serious loss:

  Authorization, not authentication. Login usually works. What fails is the per object ownership check: an id arrives from the browser, the handler acts on it without asking whether the
  signed-in user owns it. This is the single most common cause of cross-tenant data loss in web apps.

  Credential handling. Long lived, broad scope, silently usable credentials that leak into logs, backups, error reports, subprocess environments, or a component that had no business holding
  them. Compounded by no rotation story, so a suspected leak has no cheap response.

  Trust boundary drawn in the wrong place. Not a bug in any one line. A component holds more privilege than its inputs justify, so it becomes a confused deputy: it faithfully executes what an
  untrusted party asked for, with authority that party lacks.

  Injection at a parser boundary. Any place where structured meaning is built by string concatenation: SQL, shell, HTML, search query languages, template engines, and now natural language
  prompts. The tell is that data and control share a channel with no escaping contract you can rely on.

  Multi-step flows. OAuth callbacks, checkout confirmation, account linking, password reset. Each step has to be bound to the session and to the previous step. Missing bindings give you
  replay, code substitution, and "link the attacker's object to my account" bugs. Races belong here too.

  Failing open. Exception handlers that swallow a verification error and continue. Fallbacks that substitute a less safe path when the safe one is unavailable. Positive verdicts cached on a
  key that is too coarse. This class is dangerous because the system looks healthy while enforcing nothing.

  Operational and supply chain. File modes, service accounts, exposed ports, stale hosts, dependencies pulled by tag, secrets in a unit file. Boring and constant.

  Deletion and retention. Data that survives account deletion, or lives in a place nobody enumerated. Rarely exploited, frequently a legal and reputational problem.

  How to prioritize in general

  Do not rank by CVSS or scanner counts. Rank by three questions asked in order.

  1. Who can trigger it. Anonymous internet, any registered user, a user who already has some relationship to the victim, or the operator. Each step down that list is roughly an order of
  magnitude less urgent.
  2. What it yields. Cross-tenant read or write, persistent credential, code execution, one user's own data, denial of service, information disclosure with no direct use.
  3. What must already be true. Preconditions that the attacker controls are not mitigations. Preconditions that require luck or insider access are.

  That gives a working order: pre-auth remote execution or cross-tenant access, then authenticated cross-tenant access, then persistent credential exposure, then privilege escalation inside a
  tenant, then self-inflicted or operator-only issues, then availability.

  Two modifiers worth applying on top:

  Detectability. A bug that leaves no trace is worse than an equally severe one that writes an audit row, because it changes what you can say after the fact and whether you can bound the
  damage.

  Fix durability. Prefer fixes that remove the class over fixes that patch a call site: a single chokepoint that all callers must pass through, a type that makes the unsafe state
  unrepresentable, or a test that fails in CI when the invariant breaks. A finding whose fix is "remember to check this in every new handler" has not really been fixed.

  Also useful: separate severity from confidence. A confirmed medium beats a speculative critical for scheduling purposes, and speculative findings should be verified before they consume
  anyone's time.

  For this class of app specifically

  A multi-tenant agent holding Gmail refresh tokens, driven by content strangers write, calling out to inference providers. The threat ranking is not the generic web one.

  1. Cross-account access. Highest, because the asset is other people's mailboxes. Every route and every account mutator must derive the account identity from the session, never from a path
  segment, form field, or webhook payload. The dangerous shape is any function that takes an account id as a parameter and is also reachable from a request. Related: background jobs that
  sweep all accounts and could deliver one account's result to another's Telegram target or draft.

  2. Refresh token custody. A Gmail refresh token is persistent, broad, silent, and survives your redeploys. It ranks above nearly every conventional web bug because compromise is unbounded
  in time and invisible to the victim. Things worth watching: any code path that materializes a plaintext refresh token into a long lived object, any log or exception that could carry one,
  and whether a compromise of a single component yields readable tokens. Split custody only pays off if the layer order holds and there is no bypass; a bypass added for availability reasons
  converts the whole design back into one box that can read everything.

  3. OAuth and linking flow integrity. State binding, PKCE, redirect allowlist, and the ownership test on anything the browser hands back: a checkout id, a link token, a chat id. The generic
  bug here is "user submits an identifier for an object they do not own, system links it to their account". It applies to billing, to Telegram linking, and to any future integration.

  4. Prompt injection and tool capability. Email bodies are attacker controlled by definition: anyone who knows the address gets to put text in front of your model. Assume the fence around
  untrusted content will eventually fail. So the question to prioritize is not "can the model be misled" but "what is the worst the available tools permit when it is". Rank findings by the
  capability they reach:

  - Ability to send mail to an attacker chosen recipient is the top one, because it is a direct exfiltration channel for everything the model can read.
